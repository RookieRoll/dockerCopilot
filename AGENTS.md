# Repository Guidelines

## Project Structure & Module Organization

This is a Go 1.23+ Docker management service (`github.com/onlyLTY/dockerCopilot`). The executable entrypoint is `dockercopilot.go`; application code lives under `internal/`: HTTP handlers in `handler/`, business logic in `logic/`, shared Docker/file helpers in `utiles/`, configuration in `config/`, dependency wiring in `svc/`, and API/domain types in `types/`. Runtime configuration is in `etc/dockerCopilot.yaml`. Static logos and Bootstrap assets are under `static/`, container packaging is in `docker/Dockerfile`, and CI/release workflows are in `.github/workflows/`. The embedded `front/` directory is generated by the separate React frontend build and is intentionally ignored.

## Build, Test, and Development Commands

- `go test ./internal/...` — run the package tests.
- `go test ./...` — run the full suite; it requires the generated `front/` assets because the root package embeds `front/*`.
- `gofmt -w .\internal .\dockercopilot.go` — format changed Go files (prefer targeting changed files).
- `go build -o bin\dockerCopilot .` — build the service after frontend assets are present.
- `go run . -f etc/dockerCopilot.yaml` — run locally with the repository config; Docker access and a valid `secretKey` are required.

CI builds the React frontend first, then cross-compiles Linux `amd64` and `arm64` binaries and packages Docker images. Match those targets when validating release-related changes.

## Coding Style & Naming Conventions

Use `gofmt` and idiomatic Go: tabs for indentation, lowercase package names, `PascalCase` for exported identifiers, and concise `camelCase` locals. Keep handlers thin and place Docker or persistence behavior in `internal/logic` or `internal/utiles`. Use `logx` for application logging rather than ad-hoc prints; never commit secrets or machine-specific paths.

## Testing Guidelines

Tests use Go’s standard `testing` package. Name files `*_test.go` and functions `Test<Behavior>`. Existing tests cover HTTP route authorization, uploads, and traversal-safe restore/delete paths. Add focused regression tests for security-sensitive or API changes; run `go test ./internal/...` before submitting.

## Commit & Pull Request Guidelines

Recent history uses short, imperative subjects with prefixes such as `fix:` and `fea:` (for example, `fix: 修复api`). Follow that convention, keep one logical change per commit, and avoid unrelated formatting churn. PRs should explain behavior and affected paths, include test commands/results, link an issue when applicable, and attach screenshots for UI or visual asset changes.

## Security & Configuration Tips

The service needs Docker socket access and writes persistent data under `/data`. Configure a `secretKey` of at least eight characters that is not only digits; supply it through local configuration or environment variables, never source control.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

# Container port settings after a rename

Host-network port overrides are keyed by container name. A rename therefore has two durable steps: the service records a pending rename intent before calling Docker, then migrates the override after Docker confirms the rename. If the first write fails, Docker is not called. If Docker succeeds but the migration write fails, the API reports a partial result with `renamed: true`, `portsMigrated: false`, and `renamePending: true`; the container rename is not rolled back.

The settings file keeps the existing schema version and adds an optional `renameIntents` map. Each intent records the old name, proposed new name, and canonical Docker container ID. Older settings files without this field continue to load. An unresolved intent protects both names from stale-list cleanup.

On a later complete Docker list, cleanup only resolves an intent automatically when it finds the same recorded container ID under the new name. It then moves the old-name override to the new name and removes the intent. If that same ID remains under the old name, cleanup removes the intent while keeping the old mapping. A missing ID, a different container under the new name, an ambiguous name, or conflicting mappings leaves the intent and old mapping in place. The service never assigns ports to a different container just because it reused the target name.

After a partial result, verify the original container ID and its current name in Docker, then allow a successful complete container list to retry the same-ID migration. If the original ID is missing or another container owns either name, resolve the container/name conflict first; the service intentionally preserves the settings for review instead of guessing. If task recovery records cannot be read, container listing remains available but skips port-override cleanup. A concurrent container operation or settings write likewise makes that list skip cleanup and reload the current settings.

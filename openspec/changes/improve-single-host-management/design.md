# Design

## Context

动机和完整范围见 proposal.md。本设计适用于单实例管理一个 Docker Engine：Go 服务嵌入 React，状态目录为 `/data`，现有配置和备份为文件。

关键代码证据：
- `internal/logic/container/updatelogic.go` 与 `restorelogic.go` 直接启动 goroutine；进度仅存在 `svc.ServiceContext.ProgressStore`，panic 只记录日志。
- `internal/utiles/updatecontainer.go` 在停止、改名后才 inspect；创建或启动失败没有恢复旧容器，使用可变 tag 创建，启动成功后立即清理旧容器。
- `containerslistlogic.go` 在列表读取时清理按名称保存的端口配置；更新临时改名造成原名称短暂缺失，存在误删窗口。
- `frontend/src/components/Containers.jsx` 最多轮询 60 次，错误依靠多种字段和中文文本判断；`Backups.jsx` 将恢复请求接受直接展示为成功。
- `getRemoteVersion.go` 未检查 HTTP 状态，`versionlogic.go` 的业务码 50001 被 handler 当作 HTTP 状态；`updateprogram.go` 部分失败返回 nil，发布包路径与 `start.sh` 不一致。
- 图标 handler 同时完成 HTTP、文件及映射更新；备份 JSON 按日期命名，同日覆盖。
- `fix-perf-and-stability` 已完成列表 8 路并发、连接关闭、缓存及共享客户端等改进。其 `container-listing` delta 尚在该变更中，本变更保留对应行为，不替它归档或同步规格。

本变更跨模块、涉及数据兼容和恢复策略，符合 design.md 的创建条件。

## Goals / Non-Goals

**Goals:**
- 使已有功能拥有明确的业务所有者，HTTP、任务状态和日志使用一致的结果语义。
- 用普通 Go 函数、少量窄接口和文件持久化实现可靠的单主机操作。
- 保持旧数据可读、现有操作路径可用、前后端一体发布及列表性能成果。
- 为每个重要失败路径提供可验证的结果和排障线索。

**Non-Goals:**
- 不创建通用 DAG、事件溯源、独立代理或数据库服务；不为全部 Docker SDK 方法创建接口镜像。
- 不提供应用数据事务或崩溃后自动续跑；容器恢复不等于数据卷恢复。
- 不要求通过重命名整个 `utiles` 包完成重构，按业务所有权移动实际代码。

## Decisions

### D1: 业务模块直接服务现有功能

目标依赖关系：

```text
React pages --> Shared API / task hooks --> HTTP handlers / logic
                                                   |
                                                   v
                                           Business services
                                                   |
                 +----------------+----------------+----------------+
                 v                v                v                v
             Docker SDK       Task runner       File stores      HTTP clients

svc.ServiceContext --> constructs and wires dependencies
```

建议包边界（实现可在不改变职责的前提下调整文件布局）：

| 包/边界 | 职责 | 现有能力覆盖 |
|---|---|---|
| `internal/container` | 查询、基础操作、更新步骤、配置快照、容器操作协调 | 列表/详情、启停重启、改名、指定镜像更新 |
| `internal/image` | 查询、删除、清理、更新检查 | 镜像列表、无 tag/未使用清理、定时摘要检查 |
| `internal/backup` | 配置导出、文件列表/删除、JSON 恢复 | JSON、Compose、逐容器结果 |
| `internal/settings` | 端口配置、图标文件和映射 | 端口快捷访问、自定义图标 |
| `internal/updater` | 程序版本、升级包准备、安装交接 | 自身检查与升级 |
| `internal/task` | 队列、状态、文件记录、查询、终态收尾 | 共享长任务支持 |
| `internal/observability` | 日志字段、脱敏、错误分类、HTTP 响应辅助 | 请求与任务排障 |
| `internal/config`、`svc` | 配置加载校验和对象组装 | 现有环境变量兼容 |

handler 解析/校验输入并调用 logic；logic 适配协议，调用业务服务。业务服务返回结果或分类错误，不返回 HTTP envelope、不依赖整个 ServiceContext。共享操作协调器由 svc 注入容器、镜像和备份服务，避免业务包循环依赖。

保留 Docker 官方客户端和现有假 daemon 测试。只围绕更新/恢复所用的 inspect、pull、create、start、stop、rename、remove 操作定义消费者侧窄接口，便于控制故障；简单查询可以直接使用 SDK。相较多层 repository/usecase/interface 模板，此选择让抽象与实际故障边界对应。

### D2: 轻量任务执行器与文件记录

每个任务独立 JSON 文件：`/data/tasks/<uuid>.json`，带 `schemaVersion: 1`。任务包含 type、status、stage、原始对象标识、受保护名称、选项、阶段时间、目标镜像 ID、新旧容器 ID、错误、恢复结果、警告及批量 items。受保护的配置快照如包含环境变量只存权限受限的单独文件，不出现在公共任务响应或日志中。

采用同目录临时文件、写入、Sync、原子替换；目录权限 0700，记录/快照权限 0600。完成任务按保留期清理；活动任务以及仍保护配置或保留未解决恢复信息的任务不因数量或期限被清理。后者标记 requiresAttention，只有只读核对确认稳定或人工处理后才解除保留，配套文档明确处理与释放条件。进度百分比可节流写入，接受、破坏性步骤开始前、阶段结束、最终结果必须持久化。

状态固定为 `queued`、`running`、`succeeded`、`failed`、`interrupted`。`stage` 表示业务步骤；`recovery.status` 表示 not-needed/restored/failed/unknown；`warnings` 表示更新成功后的清理问题。批量任务有 success/failed/skipped 计数，存在失败项则总状态 failed，成功项仍保留。终态不可被后续进度覆盖。

先保存 queued 记录再响应接受；文件写入失败或队列满时不启动任务。执行器负责 panic 收尾，任务结束使用统一 finalize 入口。关键记录写入失败时停止开始新的破坏性步骤；若旧容器已停止，可使用内存快照进行一次受限恢复，并通过独立标准输出记录存储故障，不能声称已经可靠保存结果。

启动时读取记录，将普通 queued/running 任务标记 interrupted，保留对象标识和阶段；对相关容器做只读状态核对，向用户呈现可操作的恢复信息，不自动重放删除、替换或启动。唯一例外是有完整 pending-install 标记的自身升级任务，交给 D9 的版本确认流程，在完成确认前不抢先写入终态；准备阶段中断且无交接标记的自身升级任务仍按普通中断处理。损坏记录保留在隔离目录并告警，不能悄悄当作成功或空记录。

默认值集中配置：并发长任务 2、排队容量 100、容器更新/恢复任务超时 30 分钟、终态记录保留 7 天并上限 1000 条。允许调整；批量任务受同一并发额度约束，父任务不占住 worker 等待子任务而产生死锁。普通查询、端口保存、单个启停/改名/删除继续同步，有请求超时。批量修改在服务端执行，结果不依赖浏览器保持连接。

选择文件存储以适应单实例和已有部署习惯；SQLite 的查询/事务能力暂不值得增加依赖。该记录用于查询和诊断，不构成与 Docker 的分布式事务。

### D3: 操作协调保持小而明确

对单容器修改使用原 ID 与名称对应的操作占用标记；更新创建新容器后补充新 ID 别名，结束前保护新旧身份。相同容器重复更新返回现有任务 ID；不等价的冲突操作返回 HTTP 409 和关联任务 ID，避免隐式排队改变用户意图。队列中的更新也占用目标，超时/失败释放占用。

多容器操作逐项获得占用，不持有全部目标锁等待；备份获取每个对象的短期配置快照，遇到已进入替换步骤的对象明确报告冲突或未备份，不悄悄备份临时名称。镜像删除与正在拉取/使用/保留作恢复用途的镜像协调；强制删除也不能绕过本服务活动更新的保护。

内部协调无法锁住外部 Docker 客户端。停止、改名、创建、清理前重新核验对象 ID、名称、运行状态及所有权；发生外部冲突时终止相关步骤并报告，不删除无法确定归属的容器。

### D4: 更新服务用固定步骤和有限补偿

```text
Preflight --> Snapshot --> Pull --> Resolve image ID
                                      |
                                      v
                              Stop / Rename old
                                      |
                                      v
                                Create new
                                      |
                                      v
                              Start / Verify
                                      |
                                      v
                                  Commit --> Cleanup
```

- 预检查目标、镜像引用、请求选项和 Docker 可达性；在停止旧容器前 inspect，保存原名称、运行状态、配置、挂载、网络和原镜像 ID。
- 拉取完成后解析并固定目标镜像 ID，创建时使用该 ID。配置复制只修改为更新必需的字段；避免无条件清空用户显式 hostname，网络配置需移除仅属于旧实例的运行时标识并保留用户声明部分。
- 使用原容器 StopSignal 和有限等待时间，保留原运行意图。原容器停止则新容器保持停止；原容器运行才执行启动及验证。
- 新容器创建返回的 ID 立即保存，后续操作按 ID；调用超时后先核对 Docker 实际状态，再判断成功/失败，不盲目重试 create/remove。
- 原容器运行且有 healthcheck 时等待 healthy；无 healthcheck 时默认观察持续 running 10 秒，明确这是进程存活验证。健康等待默认 120 秒可配置，受任务总期限约束。
- 创建或启动失败且所有权、配置状态可判断时，移除本任务创建的失败实例、恢复旧名称，并按原运行状态启动旧容器。恢复有独立的短期限，不能复用已过期上下文。外部冲突、状态不明或恢复失败时保留证据和剩余容器，提供人工处理信息。
- 旧容器在提交成功后才清理。清理失败使任务 succeeded 并带 warnings；新容器启动失败而旧容器恢复成功仍是更新 failed，recovery=restored。
- 请求 `delOldContainer` 使用可选 bool：显式请求优先，未提供时沿用 `DelOldContainer` 环境默认。快照与回滚不包含数据卷内容，UI 和日志不承诺撤销应用数据迁移。

相较通用工作流引擎，固定步骤更适合目前有限的业务类型；用步骤函数和故障注入测试覆盖即可。

### D5: 端口配置生命周期与更新协调

继续使用按名称关联的 `/data/config/container-port-overrides.json`。更新开始时登记受保护的原名称，成功后新容器沿用原名称；失败和中断期间保留保护，直到只读核对确认原/新实例已稳定或用户明确处理。

列表查询仍可触发孤儿清理，但清理使用完整 Docker 列表加受保护名称，并核验操作协调版本。若列表获取期间发生更新/改名，放弃本次清理并重新取快照，避免释放保护后旧列表误删配置。真正的孤儿在下一次稳定且成功的列表刷新时清除。用户改名由容器服务协调 Docker 改名与映射迁移；迁移失败保留可重试信息和旧配置，不能当作完整成功。

保留已发布 TCP 链接、未发布/UDP 语义、host 手工配置及排序去重规则。已有 spec 的同名端口生命周期要求整体更新，其他要求保持不变。

### D6: 各已有业务的结果与文件边界

| 业务 | 设计 |
|---|---|
| 备份/Compose | 按容器获取一致配置快照，任务记录逐项结果；时间戳加随机后缀命名，临时文件完成后才发布为可见备份。保留现有 JSON 数组与 Compose 格式。 |
| JSON 恢复 | 先验证完整输入，再逐项拉取/创建，记录成功、失败、跳过。名称已存在不覆盖，报告冲突。继续保持当前创建但不自动启动的行为。 |
| 备份文件管理 | 统一 BACKUP_DIR 和路径校验，拒绝越界/符号链接逃逸，读取中的备份不能被并发删除；删除不存在文件返回明确结果。 |
| 镜像删除/清理 | 服务端重新检查使用状态，逐项执行并汇总；普通删除冲突返回 409，force 仅在显式请求时生效。默认清理不强制删除。 |
| 更新检查 | 维持启动和每小时检查，防止检查任务重叠。记录镜像、registry、耗时、最后成功时间及失败原因，失败保留上次结果但标记陈旧。 |
| registry 网络 | 默认验证 TLS，可配置受信任 CA；测试显式信任测试 CA。区分应用摘要检查路径与 Docker daemon 拉取路径，代理和加速配置不能被误表述为相同。 |
| 图标 | 由 settings 服务集中处理大小/格式校验、UUID 文件、映射加锁与原子替换。保留 imageLogos.js 和静态 URL，读取时只解析允许的映射格式，不执行 JS。失败回收本次文件并保留旧映射。 |

配置备份包含环境变量等敏感内容，不向日志打印完整备份；新备份文件权限 0600。系统不自动迁移用户手工创建的整个数据目录权限。

### D7: HTTP 与前端协议兼容

保留 `code/msg/data`，为错误增加稳定 `errorCode` 与 `requestId`。公共任务 ID 字段统一保留既有 `taskID` 拼写；结构化日志使用 `taskId`，二者值相同。HTTP 只使用合法状态：参数 400、认证 401、冲突 409、服务依赖不可用 503、内部失败 500、超时 504。业务码可留在 body，不能传给 WriteHeader；GetRemoteVersion 的原始错误必须返回并记录。

接口计划（所有管理接口保持 JWT 鉴权）：

| 入口 | 行为 |
|---|---|
| 现有 POST `/api/container/:id/update`、POST `/api/container/backups/restore` | 保持 HTTP/body code 200 接受语义，返回 taskID；页面等待任务终态。 |
| 现有 PUT `/api/program` | HTTP/body code 200 改为接受后台升级任务并返回 taskID；此语义变化要求外部调用方适配，新 UI 等待重启后的任务确认。 |
| GET `/api/progress/:taskid` | 保留旧字段并增加 status/stage/error/recovery/warnings/items；查询到 failed 任务仍为 HTTP 200，查询成功与业务结果分开。 |
| GET `/api/tasks` | 按容器 ID/名称、类型、状态分页查询活动和近期任务，帮助刷新后恢复。默认 50、最大 100 条。 |
| POST `/api/containers/batch` | 接受 start/stop/restart/update 和去重后的目标列表，返回任务；限制最多 100 个目标。 |
| POST `/api/images/cleanup` | 明确 dangling/unused 策略并返回任务，实际执行前重新核验目标。 |
| POST `/api/container/backup`、POST `/api/container/backup2compose` | 新 UI 的异步创建入口，返回任务。旧 GET 创建接口保留同步完成语义，调用相同业务服务。 |
| 现有查询、单项操作、图标、端口和备份删除 | 保留路径和输入兼容，统一错误处理。 |

`dockercopilot.api` 是协议定义入口，类型与 handler 同步生成/检查；HTTP helper 不得被生成覆盖。逐页统一消费新结构，保留旧字段适配直到同版本前后端整体部署完成。

前端按 containers/images/backups/icons/version 组织业务逻辑，保留登录、主题、图标和详情界面。共享 task hook 以 taskID 轮询，活动任务不设固定 60 次上限；断线退避重试并显示状态未知，不把网络错误当作任务失败。刷新后查询活动任务，终态后刷新相关 React Query 缓存。客户端同版本任务提交错误不自动重复发送，先查询已有任务。保持轮询方案，避免引入 SSE 的连接生命周期成本。

### D8: 日志是排障协议的一部分

保留 logx，输出结构化 JSON，标准输出和文件一致。日志配置先完成加载与验证再初始化；默认 `/data/logs`，保留 7 天，按天和大小轮转，单文件默认 20 MiB、总目录默认上限 200 MiB，超限清理最旧已关闭日志。默认 INFO，配置可改。磁盘写入失败必须向 stderr 发出降级信息，不递归写同一故障日志目标。

统一字段：event、requestId/traceId、taskId、operation、stage、containerId/name、imageRef/imageId、durationMs、result、errorCode、error。后台任务持有自己的 taskId，提交日志记录原请求标识，后续轮询使用各自 requestId 关联同一任务。

INFO 记录接受、阶段开始/完成、最终结果；WARN 记录可恢复重试、陈旧检查结果和清理警告；ERROR 记录失败、恢复失败和 panic；DEBUG 记录节流的下载进度。高频成功查询只保留必要访问摘要，不重复打印图标列表等内容。

禁止默认转储完整 HTTP 请求。Authorization、Cookie、secretKey、仓库凭据、带密码的 URL、代理凭据和 token 查询参数均脱敏；错误中的 URL 也经过统一清洗。请求体、容器 env 和完整 inspect/备份不进入日志。panic 堆栈允许进入服务日志，必须走相同脱敏通道。页面展示简明错误、阶段和标识，不展示内部堆栈。

保留必要原始错误原因（如 DNS、TLS、连接重置、daemon 返回文本），不靠重复包装丢失 cause。业务层负责阶段上下文，任务 finalize 负责最终错误，避免各层重复打印同一堆栈。

### D9: 自身升级采用现有启动脚本的有限交接

版本检查与升级准备共享更新源配置，默认 `RookieRoll/dockerCopilot` 的 latest/version 与对应 release；保留 githubProxy。检查 HTTP 状态、响应体上限、版本格式、资产架构；失败不更新成功缓存，不返回 nil 表示成功。

长升级以任务运行，单实例只允许一个自身升级任务。准备期间普通查询可用；安装交接前停止接受新的修改操作，等待已有修改任务排空，超过上限则本次升级失败并恢复接收，不中断正在更新的容器。安装过程不与容器更新/恢复并行退出。

发布包统一为根目录 `dockerCopilot-new`，工作流为 amd64/arm64 生成对应 tar.gz 和 SHA256 校验文件；下载到唯一暂存目录，校验后仅提取预期普通文件，限制解压大小并拒绝路径穿越/链接。缺失校验文件的旧 release 不能被新升级器安装，返回明确不支持并保持当前程序运行。校验用于传输完整性，不将同源 SHA256 误称为独立签名验证。

验证完成才原子放置新二进制并保存 pending-install 标记；当前程序返回/保存任务状态后退出，由现有容器重启策略重新调用 start.sh。脚本保留旧二进制并检查替换操作的退出码，安装失败和新程序提前退出写入启动日志及交接结果文件，不能无声进入重启循环。新程序启动后先确认 build version 与 pending 目标匹配、HTTP 服务已就绪，再将任务标记成功；确认有独立期限，失败标记中断/安装失败，保留旧文件和明确手工恢复路径。若新程序无法启动，恢复到可运行程序后根据交接结果完成失败确认。本设计不增加常驻监督进程，也不保证启动失败时自动回退。

未配置自动重启、只读文件系统或不可写工作目录时，在交接前拒绝在线升级并说明部署前提。容器重启后已有其他未完成任务仍按 D2 标记 interrupted；正常排空时不应产生此类任务。

### D10: 测试与构建沿用现有体系

使用假 Docker daemon 覆盖阶段失败、超时后成功、外部冲突、回滚失败、配置保留、批量部分失败和镜像保护。使用 httptest 模拟版本/下载/registry 错误；使用临时目录验证原子文件、进程重启记录和日志脱敏。前端测试覆盖任务接受/完成、断线恢复、消息展示和各页面能力。

保留列表 8 路并发、端口排序去重和缓存相关回归。现有测试能力足够时不重复建立框架；生产 TLS 验证启用后修正测试 CA 信任。执行内部/完整 Go 测试、前端测试和构建，以及 Linux amd64/arm64 包布局检查。竞态测试在具备 C 工具链的 CI/Linux 环境运行，本机不可用时明确报告，不将普通测试写成 race 已通过。

## Risks / Trade-offs

- 文件与 Docker 无共同事务：持久记录提供诊断与有限核对，重启不自动重放破坏性动作；不明状态保留旧容器和配置。
- 配置恢复无法撤销卷内数据变化：明确显示恢复范围，不在失败时删除卷。
- 单实例文件锁不能保护多实例：部署约束为单实例独占管理状态目录；启动检测数据目录占用并拒绝第二个写入实例。
- 新日志可能包含错误字符串中的秘密：白名单字段与统一脱敏结合，加入凭据注入回归用例。
- 旧客户端可能误读自身升级接受响应：保持旧路径和字段，发布时前后端一起部署，新 UI 明确等待终态；外部调用方按 proposal 中的 BREAKING 说明适配。
- 图标、端口配置在回退后仍需可读：保留既有格式，新增数据使用独立目录和 schemaVersion，不能覆盖为旧程序不可识别的格式。
- 自身升级依赖重启策略与可写工作目录：前置检查和文档列出条件；安装标记与旧二进制保留支持人工恢复。

## Migration Plan

这是同一目标的部署/回退安排，不是产品分期。

1. 实现前核验现有接口和数据样本，记录兼容测试；保留当前另有的更新源三处改动，不覆盖用户变更。
2. 新增文件状态目录，旧配置原位兼容读取；新增配置均提供默认值，环境变量统一在启动时解析并保留既有名称。
3. 同一版本发布后端与嵌入式前端；先使 release 包和校验文件满足新升级器要求，再将该版本作为可在线升级目标。
4. 验证新旧接口、数据目录和包布局后部署。启动发现旧任务记录不存在属于正常情况；发现活动旧记录按中断规则处理。
5. 代码回退使用保留的旧镜像/二进制，旧配置不需逆迁移；新增任务/升级记录保留用于诊断，不删除用户数据。若已经切换业务容器镜像，程序代码回退不自动回滚业务容器。

# Spec Delta

## Purpose

定义单主机容器查询、基础操作和镜像替换的可观察行为，使用户能够可靠更新容器、判断实际结果，并在失败时了解旧容器是否恢复，同时维持现有页面和接口能力。

## ADDED Requirements

### Requirement: 现有容器查询与基础操作兼容
系统 SHALL 保留容器列表、详情、启动、停止、重启和改名能力，保留现有列表字段及端口语义，成功响应 code 为 200。未认证的修改请求 MUST 被拒绝；Docker 查询失败 MUST 返回明确错误，不能呈现为成功的空列表。

#### Scenario: 查询已有容器
- **WHEN** 已认证用户查询运行和停止的容器
- **THEN** 返回完整列表，包含现有状态、镜像、时间、端口和手工端口字段，详情仍可访问

#### Scenario: Docker 不可用
- **WHEN** Docker 列表查询失败
- **THEN** 返回合法的错误 HTTP 状态、可读原因及诊断标识，已有页面数据不被误解释为容器全部删除

### Requirement: 同一容器的修改操作协调
系统 MUST 协调同一容器的更新、启停、重启和改名；等价重复更新 SHALL 返回已有任务标识，不等价冲突 SHALL 返回 409 和冲突信息。队列中的更新及更新产生的新旧容器身份 SHALL 纳入保护，终态后释放普通操作占用。

#### Scenario: 重复提交同一更新
- **WHEN** 同一容器、镜像及选项已有待执行或执行中的更新
- **THEN** 返回同一任务标识，不启动第二次替换

#### Scenario: 更新过程中停止或改名
- **WHEN** 用户通过单项、详情或批量入口修改正在更新的容器
- **THEN** 冲突项返回明确冲突结果和关联任务，不与更新并行修改该容器

### Requirement: 更新前准备与镜像身份固定
更新 SHALL 支持原镜像和指定镜像/tag，在停止旧容器前完成参数校验、配置快照和镜像拉取。创建新容器 MUST 使用本次已解析的镜像身份，不能因 tag 后续变化而使用不同镜像。

#### Scenario: 拉取失败
- **WHEN** 目标镜像拉取失败
- **THEN** 任务失败并记录原始原因，旧容器保持原名称、配置和运行状态

#### Scenario: 拉取后 tag 被其他操作改变
- **WHEN** 本次拉取完成后同名 tag 指向另一个镜像
- **THEN** 新容器仍使用本次任务确定的镜像 ID

### Requirement: 保留配置与运行意图
更新 MUST 保留用户容器配置、挂载、网络及显式 hostname 等设置，仅转换新实例必需的运行时字段；停止过程 SHALL 尊重原停止配置。原本运行的容器更新后 SHALL 验证运行状态，原本停止的容器 SHALL 保持停止。

#### Scenario: 更新停止的容器
- **WHEN** 更新前容器处于停止状态
- **THEN** 新容器以目标镜像和保留配置创建并保持停止，任务说明未执行应用运行验证

#### Scenario: 自定义配置保留
- **WHEN** 原容器有自定义 hostname、挂载、网络和停止信号
- **THEN** 新实例保留这些用户设置，更新停止旧实例时遵循原停止信号

### Requirement: 明确更新验证与成功条件
运行中容器更新后，有健康检查时 SHALL 在期限内等待健康，无健康检查时 SHALL 验证持续运行并说明验证范围。只有满足对应条件才 SHALL 提交更新成功并开始旧容器清理。

#### Scenario: 启动后立即退出
- **WHEN** 启动调用成功但新容器在验证窗口内退出
- **THEN** 更新不能被标记成功，并进入可执行的恢复流程

#### Scenario: 没有应用健康检查
- **WHEN** 新容器没有健康检查且通过持续运行验证
- **THEN** 任务可以成功，但结果明确仅验证容器持续运行，不声称验证了应用全部功能

### Requirement: 失败恢复与不确定结果处理
替换失败后，系统 SHALL 在对象归属和状态可确认时尝试恢复旧名称及原运行状态；恢复结果 MUST 独立记录。超时或外部操作导致结果不确定时 MUST 先核对实际状态，不能盲目重试创建或删除。无法安全恢复时 MUST 保留相关容器和诊断信息。

#### Scenario: 新容器创建失败而旧容器已改名
- **WHEN** 创建新容器失败且旧容器仍可确认归属
- **THEN** 尝试恢复旧名称及原运行状态，任务保持更新失败并明确报告恢复成功或失败

#### Scenario: 创建响应超时但对象已存在
- **WHEN** 创建请求超时而 Docker 中已存在本任务创建的新容器
- **THEN** 核对该对象后继续或报告不确定状态，不重复创建另一个实例

#### Scenario: 外部占用原名称
- **WHEN** 恢复时发现原名称被不属于本任务的容器占用
- **THEN** 不删除外部容器，报告恢复受阻并保留旧容器以便人工处理

### Requirement: 旧容器保留策略与清理结果
显式 delOldContainer 请求 SHALL 优先于全局默认，未提供时 SHALL 保持全局默认行为。清理 MUST 发生在更新确认成功之后；清理失败 SHALL 作为成功任务的警告，不能误报服务替换失败。更新与恢复 MUST NOT 删除数据卷或承诺撤销卷内数据变化。

#### Scenario: 请求保留旧容器
- **WHEN** 显式请求 delOldContainer=false 且更新成功
- **THEN** 保留旧容器并在结果中返回其标识

#### Scenario: 清理旧容器失败
- **WHEN** 新容器验证成功但旧容器删除失败
- **THEN** 任务状态为成功并附清理警告、旧容器标识及错误原因

### Requirement: 批量操作逐项报告
批量启动、停止、重启和更新 SHALL 由服务端接受并执行，限制目标数量及并发，去重目标，并返回每项成功、失败或跳过的结果。单项失败 MUST NOT 被统一成功文案掩盖。

#### Scenario: 批量更新部分失败
- **WHEN** 三个更新目标中两个成功、一个失败
- **THEN** 总任务报告部分失败并包含三项结果，已成功项不被撤销，失败项保留原因和恢复结果
